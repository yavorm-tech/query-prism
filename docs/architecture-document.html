Query Prism architecture, as built and as it should evolve

Companies upload documents (PDF, Office, images, audio and video) into team-scoped topics. Query Prism chunks, embeds and graph-indexes them, then answers questions with cited sources using hybrid vector and knowledge-graph retrieval. This document reviews the code in this repository against the 12 GDE architecture domains. For each domain it records the current state, the gaps and the target design.

Domain 01

Requirements & Domain Analysis

Partial

Functional requirements

  • Tenancy: register a company, invite users by email (24 h token), organise users into teams with owner / admin / member roles, and sign in with Google OAuth.
  • Knowledge capture: upload PDF, DOCX, images (OCR), audio and video (Whisper transcription), CSV, TXT and MD into a team topic with team or company visibility, and track ingestion status.
  • Question answering: ask questions scoped to all teams, one team or one topic; get a streamed answer (SSE) with cited source chunks; keep per-topic question history.
  • Commercial: enforce per-plan quotas on queries, storage, teams and users; pick the LLM by plan; show a usage dashboard; take enterprise contact requests.
  • Governance: keep an audit log of security-relevant events per company and team.

Domain 02

Architecture Styles & Patterns

Gap

The system is deployed as microservices, but the services share one database schema, duplicate each other's code and call each other synchronously on the hot path. That gives it the operational cost of microservices without independent deployability or failure isolation.

As built

  • 5 services, each with router → function module → raw SQL
  • Every service except notification reads and writes tables owned by others
  • topics.py and cache.py are byte-identical in chat and ingestion; auth.py is identical in 4 services, audit.py in 3
  • Sync HTTP to billing on every chat request (check → LLM → increment)
  • Async only for ingestion (Celery on Redis)

Target

  • Modular monolith (one FastAPI app) with one package per bounded context
  • Hexagonal inside each module: domain → application services → ports; adapters for Postgres, Neo4j, LLMs
  • Schema-per-context in Postgres; cross-context reads only through a module's public interface
  • Domain events (DocumentIngested, QuestionAnswered) via an outbox
  • Ingestion worker stays a separate deployable, because its CPU and memory profile differs

Deferred

Full CQRS, a dedicated message broker (RabbitMQ or Kafka) and splitting retrieval into its own service are deferred to Phase 3. They become worth it only when retrieval needs GPU or replica scaling that is independent of the CRUD API.

Diverged duplicate

ingestion/app/services/graph/ner.py extracts entities with GPT-4o-mini, while chat/app/services/graph/ner.py uses spaCy en_core_web_sm. The graph is indexed with one entity vocabulary and queried with another, so graph retrieval silently misses on names spaCy segments differently, and on any non-English text. This is a concrete cost of copy-pasting instead of sharing a kernel.

Target domain model

Today every function passes dicts straight from asyncpg to the router. Invariants such as "a document belongs to exactly one team in the same company as its topic" live in SQL or nowhere. The sketch below shows the core aggregates with their invariants made explicit.

retrieval/domain/model.py · knowledge/domain/model.py
from dataclasses import dataclass, field
from enum import StrEnum
from uuid import UUID

class Visibility(StrEnum):
    TEAM = "team"
    COMPANY = "company"

class DocStatus(StrEnum):
    PENDING = "pending"; PROCESSING = "processing"
    COMPLETED = "completed"; FAILED = "failed"

# Value object: who may see what. Replaces _build_access_filter(dict).
@dataclass(frozen=True)
class RetrievalScope:
    company_id: UUID
    team_ids: frozenset[UUID]
    is_admin: bool
    topic_id: UUID | None = None

    def narrow_to_team(self, team_id: UUID) -> "RetrievalScope":
        if not self.is_admin and team_id not in self.team_ids:
            raise ScopeViolation(team_id)
        return RetrievalScope(self.company_id, frozenset({team_id}), self.is_admin, self.topic_id)

# Aggregate root: Document owns its chunks; status transitions are guarded.
@dataclass
class Document:
    id: UUID
    company_id: UUID
    team_id: UUID
    topic_id: UUID | None
    visibility: Visibility
    size_bytes: int
    status: DocStatus = DocStatus.PENDING
    events: list = field(default_factory=list)

    def complete(self, chunk_count: int) -> None:
        if self.status is not DocStatus.PROCESSING:
            raise InvalidTransition(self.status, DocStatus.COMPLETED)
        self.status = DocStatus.COMPLETED
        self.events.append(DocumentIngested(self.id, self.team_id, chunk_count))

# Port: retrieval depends on this, not on asyncpg or the neo4j driver.
class CandidateSource(Protocol):
    async def candidates(self, q: "Question", scope: RetrievalScope, k: int) -> list["Candidate"]: ...

Critical: broker on an evicting cache

Redis runs with --maxmemory 512mb --maxmemory-policy allkeys-lru and serves as both the Celery broker and the answer cache. Under memory pressure Redis may evict queued ingestion tasks, and documents then sit in pending forever. Use a separate Redis instance or DB with noeviction for the broker, and keep LRU for the cache only.

Critical: no ANN index

init.sql only has the HNSW index as a comment ("build manually after bulk ingestion"), and no migration creates it. The retriever orders by embedding_hv <=> $1::halfvec, so every query scans all chunks across all tenants. Each chunk also stores the embedding twice (fp32 ≈ 12 KB and fp16 ≈ 6 KB). Drop the fp32 column once the halfvec index exists.

Data flow

Ingest: API stores the file on the volume and inserts documents (pending) → Celery task → worker extracts text → chunks → embeds in batches of 100 → inserts chunks → NER and relations → MERGE into Neo4j → status completed. Query: billing check → cache → embed query → pgvector top 20 ∥ Neo4j 2-hop top 20 → Cohere rerank to 8 → token-bounded context → LLM → history and counter → cache. Postgres and Neo4j writes are not coordinated. A worker crash between them leaves chunks without graph entities, and nothing reconciles them.

Domain 05

API Design

Meets

REST + Server-Sent Events. REST fits the CRUD-shaped resources (topics, documents, teams). SSE is the right choice for one-way token streaming: it works through Nginx with proxy_buffering off, reconnects natively and needs no WebSocket upgrade path. GraphQL would add little because the screens map almost one-to-one onto resources.

Domain 06

Security Architecture

Gap

The application-level design is sound: bcrypt passwords, hashed single-use reset tokens, RBAC with owner / admin / member, and tenant filters on every retrieval query. The deployment undermines it.

Sensitive data and compliance

  • Customer documents are the crown jewels. They may contain PII, contracts or health data. Chunks are sent to OpenAI (embeddings and NER), Cohere (rerank) and Anthropic or OpenAI (answers). Each is a GDPR sub-processor and needs a DPA and a listing in the privacy page.
  • At rest: no encryption is configured for the Postgres or Neo4j volumes or for uploads. Use encrypted host disks at minimum. Enterprise buyers will ask for per-tenant keys.
  • Right to erasure: deleting a document removes chunks from Postgres. Verify that Neo4j entity nodes linked only to that document are also removed, and that cached answers containing its text are purged.
  • Prompt injection: uploaded documents are inserted into the LLM context verbatim. Keep the system prompt's instruction to answer only from sources, and never give the answering model tools or credentials.

Horizontal vs vertical: the API is stateless apart from the in-memory rate limiter, so it scales horizontally once that limiter moves to Redis. Workers scale horizontally by queue. Postgres scales vertically first (it already has 8 GB), then with read replicas for retrieval. Neo4j scales vertically only on the Community edition.

Consistency: strong consistency inside Postgres for identity, workspace and metering. Eventual consistency between Postgres chunks, the Neo4j graph and the answer cache, made explicit by driving them all from DocumentIngested. A nightly reconciliation job compares chunk IDs in Postgres with Chunk nodes in Neo4j. Because Neo4j is a derived index, it can always be rebuilt from Postgres.

metering/application/reserve.py: atomic quota reservation
async def reserve_query(conn, company_id: UUID) -> Reservation:
    row = await conn.fetchrow("""
        UPDATE metering.usage_counters u
           SET queries = CASE WHEN u.period < date_trunc('month', now()) THEN 1
                              ELSE u.queries + 1 END,
               period  = date_trunc('month', now())
          FROM metering.plans p
         WHERE u.company_id = $1 AND p.plan = u.plan
           AND (p.max_queries IS NULL
                OR u.period < date_trunc('month', now())
                OR u.queries < p.max_queries)
     RETURNING u.queries, p.max_queries, p.llm_model""", company_id)
    if row is None:
        raise QuotaExceeded(company_id)          # mapped to HTTP 429 at the edge only
    return Reservation(company_id, model=row["llm_model"])

Logging and tracing

Use structured JSON logs (structlog) carrying request_id, company_id, user_id and document_id. Never log query text or chunk content at INFO, because they are customer data. Use OpenTelemetry tracing from Nginx through the API, Celery, Postgres, Neo4j and LLM calls. It is essential while the system stays distributed, and still valuable in a modular monolith because of the worker hop.

Critical alerts

  • Documents in pending for more than 15 minutes (broker loss or a dead worker)
  • LLM error rate above 5 % over 5 minutes, per provider
  • p95 time to first token above 4 s over 15 minutes
  • Daily LLM token spend above 150 % of the 7-day average
  • Postgres disk above 80 % or certificate expiry within 14 days

Pattern: put an anti-corruption layer around the model providers. Today llm.py branches on model.startswith("gpt-"), and model IDs are stored as raw strings in plan_limits. A domain-level AnswerTier (basic, standard, premium) should map to provider models inside one adapter. Then replacing a deprecated model is a config change, and failover between providers lives in one place.

Embedding lock-in

All stored vectors are tied to text-embedding-3-large. Store embedding_model on each chunk now, so a future model migration can re-embed in the background and switch per company, not as a stop-the-world rewrite.

ADR-003pgvector in Postgres as the vector storeAcceptedTenant filters, document status and ANN in one query and one transaction. A dedicated vector DB (Qdrant, Pinecone) is not justified below ~50 M chunks.
ADR-004halfvec(3072) with HNSW, fp32 column droppedProposedHalves storage with negligible recall loss. HNSW is required for sub-linear search. Alternative: request 1024-dim embeddings to cut the index 3×; decide after the eval set exists.
ADR-005Neo4j knowledge graph as second retrieval channelProposedUncertain value. Keep it while an eval measures recall uplift over vector + rerank alone. If uplift is under 3 points, replace it with Postgres entity tables and drop a whole datastore.

ADR-007Celery on Redis for ingestion, broker isolated with noevictionProposedCelery stays because retries, routing and Flower already work. The broker must never share an evicting keyspace with the cache.
